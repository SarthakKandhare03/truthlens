# Viva preparation

Likely questions about TruthLens, with short answers you can say out loud. Each points to where the
evidence lives, so you can open the code if an examiner asks "show me".

## The one-minute pitch

AI makes fake photos cheap, and detecting fakes is an arms race that detectors keep losing. TruthLens
flips the question: instead of proving what's fake, it proves what's real. A photo is fingerprinted
and signed by the capturing device the moment it's taken, and the fingerprint is anchored on a
blockchain. Anyone can later check an image: **authentic** (bit-for-bit the sealed original),
**edited** (we show exactly where), or **unverified** (no provenance, not "fake").

---

## Concept

**Why use a blockchain? Wouldn't a database do?**
A database admin, including us, could quietly edit or delete a record. A public blockchain is
append-only and publicly replicated: once a fingerprint is sealed, nobody can change it or backdate
it, and anyone can verify it independently without trusting our server. The trade-off is cost and
speed, which is why only 32-byte hashes go on-chain.

**Why not store the photo itself on-chain?**
Cost and privacy. On-chain storage is paid per byte; a photo would be very expensive, and it would be
public forever. A SHA-256 hash commits to the exact bytes just as firmly. One registration costs
about 175,000 gas (`npm run gas`).

**So can TruthLens detect deepfakes?**
No, and we say so in the UI. It proves *provenance*: which device sealed which bytes, and when, and
whether a copy has changed. An image with no record is "unverified", which is not the same as fake.
This is deliberate: cryptographic proof gives certainty, while AI detectors only give probabilities
and can be fooled.

**Can't someone just photograph a screen showing a deepfake and seal that?**
Yes. That's the "analog hole", and no provenance system fully closes it. TruthLens proves *who sealed
what, when*, not that the scene was real. Trusted camera hardware (cameras that sign inside the
sensor pipeline, as in the C2PA standard) and depth sensing narrow the gap. It's listed under
Security & limitations in the README.

**How is this different from C2PA / Content Credentials?**
C2PA (Adobe, Microsoft, camera makers) embeds a signed manifest in the file's metadata. Social
platforms often strip metadata and recompress images (WhatsApp does both), which breaks the link.
TruthLens keeps the record *outside* the file, on a public chain, and uses a perceptual hash to find
the original even after recompression or metadata stripping. The two ideas are complementary.

## Cryptography

**What exactly does SHA-256 guarantee?**
Any change, even one bit, gives a completely different hash (the tests show about half of the 256
output bits flip), and finding two inputs with the same hash is computationally infeasible (~2¹²⁸
work). So an exact hash match proves "not one bit changed". Evidence: `web/test/crypto/hash.test.ts`
checks the NIST test vectors and agreement with OpenSSL.

**Where is the private key, and can it be stolen?**
It's generated by the browser's Web Crypto API with `extractable: false` and stored as a `CryptoKey`
object in IndexedDB. JavaScript can ask the browser to *sign* with it but can never read its bytes,
so it can't be copied off the device; the tests prove `exportKey` fails. Limit: malware running *on*
the device could still use the key to sign. Hardware attestation (Android Key Attestation, iOS App
Attest) would prove a key lives in genuine secure hardware. That's future work.

**Why ECDSA P-256 and not secp256k1, Ethereum's curve?**
P-256 is what browsers (Web Crypto), phone secure enclaves and passkeys support natively, which is
what makes a non-extractable key possible. Signatures are verified off-chain by our server (and could
be by anyone); some EVM chains, including Polygon PoS, offer a P-256 verification precompile
(RIP-7212), so a future version could verify signatures on-chain too.

**What is "domain separation" in the signed message?**
The device signs `"TruthLens/capture/v1" ‖ 0x00 ‖ sha256`, not the bare hash. That fixed prefix
means a TruthLens signature can't be replayed as a signature over something else, and vice versa. A
test proves a signature over the bare hash is rejected.

**What stops someone from swapping in their own key and signature?**
The SHA-256 of the device's public key is stored on-chain. Verification checks that the stored key
matches that fingerprint *and* that the signature is valid for the actual bytes. A test simulates
this attack (`web/test/crypto/proof.test.ts`): the forged signature is mathematically valid for the
attacker's key, but the key doesn't match the chain, so it fails.

## Perceptual hash and heatmap

**Why do you need a perceptual hash at all?**
SHA-256 can't recognise a copy: resizing or recompressing (e.g. WhatsApp) changes every byte. A
perceptual hash describes what the picture *looks like*, so a re-shared or edited copy can still be
linked to its original. It's a 64-bit DCT hash: grayscale → shrink to 32×32 → frequency transform →
keep the 8×8 lowest frequencies → one bit per coefficient (above or below the median).

**Why is the threshold 16 bits?**
It was measured, not guessed (`npm run phash:report`). Recompression and resizing change 0–2 bits;
filters up to 14; small edits 4–16; unrelated images 22–38. So 16 accepts every benign change and
most realistic edits while staying well clear of unrelated photos. For random hashes, the chance of
two landing within 16 bits is about 1 in 26,000.

**What if an unrelated photo matches by chance?**
There's a second, independent check: the pixels. The verifier loads the stored original and compares
them; if more than 45% of the image differs it isn't treated as an edit (measured: unrelated images
53–59%, the biggest genuine edit tested about 31%). And among several candidates, the one that
explains the image with the *least* pixel change wins.

**How is the heatmap computed?**
Resize both to the same size (aligns resized copies), convert to grayscale and blur slightly (removes
JPEG noise), undo any whole-image brightness/contrast filter with a *robust* fit (it ignores the
edited pixels), then count pixels that still differ by more than 20 levels in each of the 16×16 grid
cells. Evidence: `web/src/lib/image/diff.ts` and `npm run diff:report`.

**What are its weaknesses?**
Crops shift the framing, so the heatmap becomes scattered; mirrored images don't match at all; an
edit that only changes colour at the same brightness is under-reported. Feature-based matching
(ORB/SIFT keypoints) would handle crops and is listed as future work.

## Blockchain and backend

**What does the smart contract store?**
Per photo: SHA-256, perceptual hash, the public-key fingerprint, a pointer to the stored original,
the relayer address, and the timestamp and block number set *by the chain*, so they can't be
backdated. Plus optional parent links for edit chains. See `blockchain/contracts/TruthRegistry.sol`.

**What is the relayer, and isn't it a central point of trust?**
It's the server's wallet that pays gas, so users never need crypto. It checks the device signature
before writing, and only allow-listed relayers can write (otherwise anyone could register a hash
first under a fake key). It *is* a gatekeeper for writes, but it can't alter or delete past records,
and anyone can read and verify the chain without it.

**What stops someone draining the relayer's funds?**
A per-IP rate limit (10 registrations per minute), duplicates rejected *before* sending a
transaction, and upload limits (15 MB, 50 megapixels, format detected from content).

**How trustworthy is the timestamp?**
It's `block.timestamp`, set by the network's validators, accurate to a few seconds. It proves the
photo existed *no later than* that block.

**What does it cost and how would it scale?**
About 175,000 gas per photo, a fraction of a cent on Polygon at typical prices. To scale further,
many hashes could be combined into a Merkle tree and only the root stored per transaction, giving
thousands of photos for the price of one, with a Merkle proof per photo.

**Why the SQLite database if the blockchain is the source of truth?**
The contract can look up an *exact* hash instantly, but not "which registered perceptual hash is
closest to this one?", which needs a scan over every hash. SQLite is a local cache for that search.
It can be deleted and rebuilt from the chain, it heals itself if the chain is reset, and every
candidate is re-checked against the chain before it's trusted.

**What happens if the stored original or proof file is lost?**
The chain record survives, but AUTHENTIC requires the signature, so the verdict becomes UNVERIFIED
("proof missing"). Storing originals in S3 (supported) or the signature on-chain or in IPFS would
remove that dependency; it's a trade-off against cost.

**Is it private?**
Only hashes go on-chain. In this demo the originals are publicly downloadable (needed for the
before/after slider, like a news archive), and photos from the same device share a key fingerprint,
so they're linkable. A private deployment would put originals behind authentication.

## Engineering

**How do you know it works?**
22 contract tests, 62 unit tests, an end-to-end script with 21 checks against the running system
(including four attack cases), and a headless-browser walkthrough on desktop, phone size and reduced
motion that fails on any browser error. Plus the measurement reports behind every threshold.

**What was the hardest bug?** (good stories to tell)
- *Stale nonce:* back-to-back transactions failed because the ethers library re-used a 250 ms-old
  cached answer from the node. Fixed by disabling that cache and only resyncing after failures.
- *Wrong original matched:* several near-identical photos had close perceptual hashes; the closest
  hash wasn't the real original. Fixed by letting the pixel comparison choose between candidates.
- *Floating-point noise:* a flat grey image gave a random-looking hash because of ~10⁻¹³ rounding
  errors. Fixed with a small tolerance; the unit test caught it.
- *Cache vs. chain reset:* restarting the local blockchain left stale cache rows that blocked new
  registrations. Fixed by making the cache heal itself: the chain always wins.

**Why Next.js for both frontend and backend?**
One codebase and one deployment: the pages and the API (which acts as the relayer) share the same
TypeScript types, so a change to the API's response shape is a compile error in the UI.

**Why does it look like a detective's evidence board?**
The design ("Night Shift") follows the subject: a photo is evidence, and TruthLens is its chain of
custody. The landing page tells the whole idea as a pin-board: an original polaroid ("device signed
✓"), a suspect copy with a red, sliced region ("hash mismatch ✕"), an evidence tag showing the
latest real seal from the chain, and a VERIFIED · ON-CHAIN stamp, joined by red string. Verdicts
are rubber stamps, edits are cross-hatched, the capture ends in a receipt, provenance is a film
strip, the explorer is a ledger. It avoids the generic glass-and-neon "AI product" look. The night
(dark, default) and day (light) themes share one set of CSS colour variables; a tiny script in
`<head>` applies the saved theme before the first paint, so there's no flash of the wrong theme.

**The ransom-note headline gives every letter a different font, colour and tilt. Isn't that random, and doesn't it break server rendering?**
It looks random but isn't: each letter's font, size, colour and tilt are computed from its position
in the sentence (for example the tilt is `((i × 7 + 3) mod 13) − 6` degrees). `Math.random()` would
give the server and the browser different letters, and React would report a hydration mismatch.
The `<h1>` keeps the real sentence in its `aria-label` and hides the cut-out letters from screen
readers, so it still reads as "Every pixel has a witness".

**What is live camera verify, and why can't it say AUTHENTIC?**
You point a phone at a photo (on another screen or on paper) and TruthLens finds its sealed original in
real time. The phone hashes each camera frame at 270 crops (2 photo shapes × 5 zooms × 9 shifts × 3
small rotations) and sends only those 64-bit perceptual hashes to `/api/match`; the picture never leaves
the device. A sealed photo is "locked" when it is the closest match within 11 bits in 3 of the last 6
frames. It can't say AUTHENTIC because a re-photographed image has completely new bytes: live mode
*finds* the original and its on-chain record, and uploading the file gives the bit-for-bit proof.

**Why 11 bits in live mode but 16 for file checks?**
Trying 270 crops gives an unrelated photo 270 chances to land close. I measured it (`live:report`):
at 16 bits 1% of unrelated pairs matched, at 11 bits none of 1,440 did, while 97% of real re-captured
frames still matched. Requiring 3 of 6 frames means one missed frame doesn't matter.

**How does the red string stay attached when you drag a polaroid?**
Each pin is an element marked `data-anchor`. On every animation frame the board measures where the
pins really are (`getBoundingClientRect`, which includes rotation and drag offsets) and rewrites the
SVG path of each string, a curve that sags in the middle like real string. It writes the SVG
directly instead of using React state, so nothing re-renders 60 times a second.

**How did you keep the animations smooth?**
Only `transform` and `opacity` are animated (handled by the GPU), ambient effects are CSS keyframes,
and the 3D eye's ~11,000 halftone dots are moved by a GPU shader in a single draw call. Mouse-driven
effects (the viewfinder cursor, magnetic buttons, the headline letters that react to the cursor, the
loupe) never re-render React on every mouse move: they use Framer Motion "motion values" or write
styles directly inside `requestAnimationFrame`. The scroll marquee reads scroll *velocity*
(`useScroll` → `useVelocity` → `useSpring`) to set its speed and slant. Everything respects the
operating system's "reduce motion" setting, and cursor effects switch off on touch screens.
